Sort this repo's legacy root ledger files and, only with `--apply`, move the plugin's own ones into `.dev-team/`. Arguments: $ARGUMENTS (optional `--apply`; without it the command only reads and reports).

Every record file the dev-team suite writes for itself lives in `.dev-team/` and carries the dev-team marker on line 2 (`verdict.json` carries it as a field); a record file at that path without the marker is never written to — the run stops and asks. See `dev-team-orchestrator/references/conventions.md`, "Where the plugin writes, and the ownership rule".

Read that section before acting — especially point 5 (files from before v1.5.0, the lookup order) and point 7 (the first write into `.dev-team/`). This command is point 5 done for all seven files at once. Where this file and `conventions.md` disagree, `conventions.md` is right and this file is the bug.

**Why the command exists.** Before v1.5.0 the suite wrote its ledgers in the legacy root location (the top level of the project). Projects keep their own files with the same names — a product feature list called `FEATURES.md`, a public security policy called `SECURITY.md`, a hand-written `HANDOFF.md` — and in one real project the plugin's findings were appended to the end of the project's public security policy. So this command must never decide by a file's name alone, and must never decide by "it looks like ours" alone either. Only the marker is proof. Everything else is a question for a person.

**What it looks at.** The seven names, at the top level of the repo only: `PROJECT.md`, `FEATURES.md`, `SECURITY.md`, `VERIFICATION.md`, `MIGRATION.md`, `HANDOFF.md`, `verdict.json`. Their new homes are `.dev-team/PROJECT.md`, `.dev-team/FEATURES.md`, `.dev-team/SECURITY.md`, `.dev-team/VERIFICATION.md`, `.dev-team/MIGRATION.md`, `.dev-team/HANDOFF.md` and `.dev-team/verdict.json`. It does not look in `docs/` or `.github/`: the suite never wrote ledgers there, and a `SECURITY.md` in either place is the project's public policy.

## 1. Safety checks before anything else

1. Find the top of the repo with `git rev-parse --show-toplevel` and work from there, so "top level" means the project's top level and not whichever subfolder the session happens to be in.
2. **Outside a git repo:** the preview (steps 2–3) still runs, because it only reads. `--apply` is refused, and the command says why: the move has to be a `git mv` in a commit so it can be seen and undone, and outside git there is no commit to undo.
3. **Dirty working tree** (`git status --porcelain` prints anything): `--apply` is refused, and the command says why: the move is made as one commit of its own, and uncommitted changes would either be swept into that commit or make it hard to tell the move apart from other work. Commit or stash first, then run it again. The preview still runs. This check cannot see ignored files; section 3 checks those for the files this command would move or write. With `--apply`, record the commit id now with `git rev-parse HEAD` and write the value down in your working notes; this document calls it H0. Keep the value itself rather than relying on a shell variable such as `H0=$(git rev-parse HEAD)`, because each command may run in a fresh shell where that variable no longer exists. H0 is what the re-check after the questions and the rollback in section 4 compare against.
4. **On the default branch** (`main`, `master`, or `.dev-team/config.yml`'s `git.default-branch`): with `--apply`, say so and ask before committing there. The suite never merges to the default branch without asking, and committing straight onto it amounts to the same thing.
5. `--apply` is an explicit per-run argument, so it outranks `features.dry-run: on` in `.dev-team/config.yml` (the standard precedence chain in `config-and-toggles.md`). Without `--apply` nothing changes, whatever the config says.

## 2. Sort each file into one of four groups

Check the files in the order listed above. For each legacy root file that exists, decide its group with the tests below, **in this order** — the first test that matches decides. The tests are best-effort pattern matches. They only sort; they never give the command permission to move anything except group (a).

**Conflict first.** If `.dev-team/<name>` already exists as well, `.dev-team/<name>` wins (point 5, "Both exist"). Still sort the legacy root file so the report can describe it, but mark it **conflict — nothing will be moved** and leave both files exactly as they are. A person has to decide which one to keep.

**(a) Ours — will move.** The marker is there:
- For a markdown file: one of the first three lines contains `<!-- dev-team: ledger=<kind> schema=` where `<kind>` matches the file name (`project` for `PROJECT.md`, `features` for `FEATURES.md`, `security` for `SECURITY.md`, `verification` for `VERIFICATION.md`, `migration` for `MIGRATION.md`, `handoff` for `HANDOFF.md`), or one of the first three lines contains the legacy marker `<!-- dev-team-schema:`. Only the first three lines count, because the plugin's own documentation quotes marker lines further down inside examples, and a file that merely quotes the marker is not a ledger.
- For `verdict.json`: the file is valid JSON and has a top-level string field `"dev-team"` starting with `ledger=verdict `.
- A new-form marker that names a **different** kind (say `ledger=security` inside `FEATURES.md`) is not proof that this file is the ledger its name says. It is not (a). Run the (d) test below on it next; if that does not match, put it in group (b) and show the mismatch in the question.

**(d) Mixed — needs a person; nothing will be touched.** Checked straight after (a), before (b) and (c), so a file with records appended to it can never be offered for moving. Either:
- the file passes the shape test for its name in group (b) below **but** its first level-one heading contains "Security Policy" (for example a public security policy with a `## Findings` register below it), or
- the file has **three or more lines** carrying a dev-team record number **of the kind that ledger holds** — `FG-` for `FEATURES.md`, `F-` for `SECURITY.md`, `V-` for `VERIFICATION.md`, `M-` for `MIGRATION.md`, `B-` or `G-` for `PROJECT.md`, each followed by three digits. `HANDOFF.md` and `verdict.json` have no record kind of their own, so this second test never applies to them.

Report the line number and text of the first line that passed a shape test or carries such a record number: that is roughly where the dev-team part probably starts, and it is where a person should look to cut it into `.dev-team/<name>` by hand. Report it together with the two-way wording in the next paragraph.

For every (d) file, the report says it is "either an old dev-team ledger with no marker (add the marker on line 2 by hand and run this command again) or a project document with dev-team records added to it (cut the dev-team part into `.dev-team/<name>` by hand)". This is the two-way wording the rest of this command refers to.

- *Why the command refuses to cut it:* the boundary between the project's text and the plugin's records is a judgement about someone else's document. Getting it wrong either publishes security findings as policy or deletes part of the policy, and neither would be noticed until much later.
- *Why (d) comes before (b):* an earlier order checked (b) first. A product `FEATURES.md` with three `FG-` records appended matched (b) on its first record, so it was offered for moving and stamping as a whole, and the mixed test never ran. The same happened to a `SECURITY.md` titled `# Security` rather than "Security Policy" with three `| F-` rows. *What this costs:* an old ledger with no marker and three or more records of its own kind is also sorted (d), because the command cannot tell a whole ledger from a document with records appended. In practice that is most unmarked old ledgers that hold records at all. For example, the legacy root `PROJECT.md`, `FEATURES.md` and `SECURITY.md` of two real projects checked while writing this, all genuine dev-team ledgers with dozens of records, now land in (d) rather than (b). The person has to add the marker by hand and run the command again. Refusing here is deliberate: a wrong guess moves someone else's document, and a person adding one line by hand costs very little by comparison.
- *Rejected — a "this might be mixed" warning inside question 1:* that prompt must be copied word for word from `conventions.md` point 4, so it cannot carry an extra warning. A test on the file's title was rejected too, because old ledger titles were never fixed (the documentarian template's title is `# [Project name]`), so a title cannot tell a ledger from a product document.
- *Rejected — counting any dev-team number, of any kind:* hand-written handovers and project notes legitimately mention record numbers in passing ("OIDC provider (G-001) built"). Counting every kind of number would call those files "mixed" and send a person looking for records that are not there. Only the numbers a ledger of that name actually holds suggest that records were appended to it.

**(b) Looks like ours — ask.** No marker, but the file has the shape of the plugin's own ledger of that name, **and** nothing marks it as the project's own document. The shape tests (headings are matched ignoring case, heading level, numbering and emoji, because real ledgers decorate their headings, for example `## 🎯 Goal` or `## 6. 🎯 Findings register`):
- `PROJECT.md`: at least three `##` (or deeper) headings between them containing three different phrases from: "Goal", "Definition of done", "Stage plan", "Current status", "Decision log", "Checkpoint log", "Backlog", "Trajectory ledger".
- `FEATURES.md`: any feature-gap number (`FG-` followed by three digits), or a heading containing "In-scope gaps".
- `SECURITY.md`: a heading of any level containing "Findings" or "Coverage ledger", or a table row starting `| F-` followed by a digit.
- `VERIFICATION.md`: the text `OVERALL VERDICT`, or a table row starting `| V-` followed by three digits.
- `MIGRATION.md`: a heading containing "Stage Ledger".
- `HANDOFF.md`: a line starting `NEXT:` — the resume card's own line. A heading such as `## NEXT` does not count, because hand-written handovers use headings like that too.
- `verdict.json`: valid JSON whose top-level `overall` is `PASS`, `PASS_WITH_GAPS` or `FAIL`, with at least one of the top-level keys `claims`, `integration` or `counts`. (`counts` is there because verdict files written before the schema existed carry `counts` rather than `claims`.)

What marks a file as the project's own: its first level-one heading (the first line starting `# `) contains "Security Policy". That is the heading of a public security policy, which is exactly the file this rule exists to protect. Because (d) is checked before (b), a file carrying that heading and a ledger shape has already been sorted (d) by the time this test runs. The condition stays written here as well, so that (b) still reads correctly on its own and so that reordering the groups again could never let such a file through.

**(c) Not ours — leave alone.** Everything else. The command writes nothing to it, moves nothing, and asks nothing.

Groups (c) and (d) are never moved, and nothing is ever written into them. If a person knows a (c) or (d) file really is a dev-team ledger, they can add the marker on line 2 by hand (or cut the dev-team part out into its own file) and run this command again.

## 3. Print the table

One row per legacy root file found: the file, its group, the reason (which test matched, or "no marker and no ledger shape"), the first three lines of the file, and, for (d), the line where the dev-team part probably starts. Then list:
- any `.dev-team/<name>` that already exists (and, for a legacy root file with the same name, the conflict);
- the `.dev-team/autopilot.json` values that step 5 would rewrite, before and after.

If no legacy root file with one of the seven names exists, say so plainly and stop — there is nothing to move.

**Ignore check (before anything else changes).** This check runs even when no file will move — when every file is (c), (d), a conflict, or could still be answered "leave it" — because step 2 in section 4 can still write `.dev-team/config.yml` or an instruction file. It has two parts.

*Part 1: every path this command would write.* Run `git check-ignore -q --no-index <path>` on each of these (this list includes `.dev-team/config.yml` and the instruction files):

- `.dev-team/README.md`, `.dev-team/.gitignore`, `.dev-team/autopilot.json`, and `.dev-team/<name>` for every file sorted (a) or (b) above that is not a conflict;
- `.dev-team/config.yml`, whenever question 3 could be asked (its trigger, described in section 4 step 3, holds), because a decline writes it;
- each of `CLAUDE.md`, `.claude/CLAUDE.md`, `AGENTS.md` and `GEMINI.md` that exists and lacks the pointer sentence, because an accept edits it.

Skip any path that `git ls-files --error-unmatch -- <path>` shows is already tracked. Git adds changes to a tracked file even when it matches an ignore pattern, so refusing there would be wrong. List each ignored path that is not already tracked in the table with the conventions point 7 warning: "`<path>` is ignored by this repo's `.gitignore`, so it will not be committed and will not travel with the repo."

*Part 2: every legacy root file this command would move.* For every legacy root file sorted (a) or (b) that is not a conflict, run `git ls-files --error-unmatch -- <name>`. If it fails, the file is not tracked by git. The tree was clean, so that can only mean the project ignores it. Show the output of `git check-ignore -v --no-index <name>` in the table, which names the ignore rule, with the warning: "`<name>` is not tracked by git (ignored by the rule shown), so `git mv` cannot move it and the move could not be committed or undone."

If `--apply` was requested and either part found anything, refuse to act. Report the warnings and stop before any question and before touching anything. The fix is the person's own: change their `.gitignore` (and commit the file if it should be tracked), then run the command again. Never fall back to `git add -f`: that would override the project's own ignore decision without asking, silently.

- *Why part 2 exists:* `git status --porcelain` does not list ignored files, so the clean-tree check in section 1 cannot see an ignored legacy root file. Without this check, `git mv` failed at step 5 with "not under version control", after step 4 had already created files and earlier files in the list had already moved.
- *Why config.yml and the instruction files are on the list:* an earlier version left them out, so a declined pointer sentence could create an ignored `.dev-team/config.yml` that `git add` then refused. That left an uncommitted file nobody could see in `git status`, with no rollback. An ignored `.claude/` folder is common, and `.claude/CLAUDE.md` is one of the pointer-sentence files, so an accept could fail the same way.
- *Why already-tracked paths are skipped:* `git check-ignore --no-index` reports a tracked file as ignored if its name matches a pattern, yet `git add` still works on it. Refusing on those would stop the command for no real reason.

- *Why this runs here, before the move, and not after it (as an earlier version of this command did):* the check used to run only after `git mv` had already renamed the files. But a moved file is tracked, and `git check-ignore` never reports a tracked file as ignored — so the warning could never fire for a moved file at all. The two files most at risk when a project's `.gitignore` swallows `.dev-team/` — `.dev-team/README.md` and `.dev-team/.gitignore`, both newly created and so not yet tracked by anything — were never checked either way. The failure only showed up one step later, when `git add` refused them outright with "the following paths are ignored by one of your `.gitignore` files", by which point the working tree already had files moved out of place with no way back (see "If any step from 4 to 9 fails, or the standalone commit in step 2 fails" below). Running the check first, with `--no-index` (which checks a path against the ignore patterns regardless of whether the index already tracks something there), catches the problem before anything moves. A second check after the write stays in step 8, as a line of defence in case something changes the answer in between — an edited `.gitignore`, a newly added nested ignore file.

**Without `--apply`, stop here.** Nothing on disk or in git has changed. Say what `--apply` would do.

## 4. With `--apply`: ask, then move

If the ignore check in section 3 found anything — an ignored path this command would write, or a legacy root file git does not track — `--apply` stops there. This section is never reached until the person fixes their `.gitignore` and runs the command again.

Ask every question **before** changing anything, so a "no" halfway through never leaves a half-done move.

A file marked **conflict** in section 2 is never asked about here, whichever group — (a), (b), (c) or (d) — it also sorted into for the report: it stays a conflict, reported and left exactly as it is, and it never reaches question 1 below. And whatever a file's group, the command only ever stamps the dev-team marker onto a file it is about to move; a file it leaves in place — group (c), group (d), a conflict, or a (b) file answered "leave it" — is never written to, marker included. *Why this needs saying:* a (b) file that is also a conflict used to be asked question 1 anyway, with a prompt whose choice (a) promised to move and stamp it — a promise the conflict rule then silently broke, because conflicts are always skipped when the actual moving happens. The file was never in danger, since only the files reached below at step 5 are ever touched, but the person answering the question was told something untrue.

1. **Each (b) file that is not also a conflict:** ask with exactly this prompt (fill in the angle brackets; the two choices, "(a)" and "(b)", are the prompt's own and are not the group letters above), copied byte for byte from `conventions.md` point 4:

   > Found `<path>` but it has no dev-team marker, so I cannot tell whether it is this plugin's file or the project's own. First three lines: <lines>. Choose one: (a) "it is a dev-team file from before v1.5.0" — I will move it to `.dev-team/<name>` (if it is at the top level), add the marker, and commit that on its own; (b) "leave it" — I will write nothing to it. I will not guess.

   Choice (a) → the file joins the move. Choice (b) → it is left exactly where and as it is, and never written to. There is no third answer: if the reply is unclear, treat it as "leave it" and say so.
2. If nothing is left to move (every file is (c), (d), a conflict, or a "leave it"): no ledger will move, so there is no move commit at step 9 for question 3's answer to ride along with. Ask question 3 anyway — right here, using the exact wording below — because it is a question about the project's instruction files, not about ledger files, and whether anything moves is beside the point:
   - Question 3's trigger does not fire (no listed instruction file exists, every one that exists already has the sentence, or a decline is already recorded) → say so and stop. Nothing changes.
   - **Before writing anything for either answer below:** run "Check again that nothing changed while the questions were asked" (just before step 4) and stop if it finds anything. While writing, keep the list described in "Keep a list of every path this command touches" (also just before step 4): each instruction file edited, and `.dev-team/config.yml` as `edited` if it was tracked at H0 or `created` if it did not exist, plus whether `.dev-team/` itself was created. If any write, `git add` or `git commit` here fails, follow "If any step from 4 to 9 fails, or the standalone commit in step 2 fails" below, then report. *Why:* this small commit writes files just like the move does, so it needs the same protection against a changed tree and the same way back.
   - The user accepts → add the sentence to the agreed instruction files, `git add` them, and commit that single change on its own with the message `dev-team: add the .dev-team/ pointer sentence`. Say so in the report, then stop.
   - The user declines → write `pointer-sentence: declined` under `features:` into `.dev-team/config.yml` right now (creating a minimal file holding `version: 1` and that key if none exists yet), `git add .dev-team/config.yml`, and commit that single change on its own with the message `dev-team: record .dev-team/ pointer-sentence decline`. Say so in the report, then stop. *Why commit it even though nothing moved:* conventions point 8 says a decline is committed so it holds for every collaborator; with no move commit to carry it, this one small commit is the only way to keep that promise.
   Either way, stop here — no move happens, because there was nothing to move.
3. **Pointer sentence (point 8 of the conventions section).** Something is left to move — offer this sentence, word for word, once, when all three hold: one or more of `CLAUDE.md`, `.claude/CLAUDE.md`, `AGENTS.md` and `GEMINI.md` exists; at least one of those that exists does not already contain the sentence; and `.dev-team/config.yml` does not record an earlier decline (`pointer-sentence: declined` under `features:`). Name each of those files that lacks the sentence:

   > Dev-team plugin state and the current handover live in `.dev-team/` — read `.dev-team/HANDOFF.md` first.

   Offer it; never add it silently. None of those files present, or the config already records a decline → say so and do nothing; never create an instruction file just to hold the sentence. **During this question phase, only REMEMBER the answer** (accept and which files to add it to, or decline) — write nothing to disk here. The write happens at step 9 below, immediately before `git add`, folded into the one move commit, so a "no" to a later question in this list can never leave the sentence half-applied.
   - **A decline is remembered.** When the user declines, step 9 sets `pointer-sentence: declined` under `features:` in `.dev-team/config.yml` and tells the user so. If that file does not exist yet, step 9 creates a minimal one holding `version: 1` and that key, and says so.
   - *Why the trigger changed:* the old wording offered the sentence only "if `.dev-team/` does not exist yet, this run is the one that creates it". A project that had used the plugin before this command ever ran already has a `.dev-team/` folder, so that condition could never be true here even on a project whose `CLAUDE.md` has never once seen the sentence — the offer would be skipped for ever. The new trigger checks whether the sentence is actually missing, not whether this particular run happens to be the folder's first writer.

Once every question is answered, two things come before any change: a second clean check, and a list the rollback depends on.

**Check again that nothing changed while the questions were asked.** Do this once all questions are answered and before step 4 (and before the writes in step 2, when that path is taken). Run `git status --porcelain --untracked-files=all` and `git rev-parse HEAD`. If the status prints anything, or HEAD is no longer H0, stop. Nothing has been changed yet. Report: "The working tree changed while the questions were being asked (list the paths). Nothing was moved. Commit or stash those changes and run the command again."

- *Why:* the first clean check in section 1 can be minutes old by now, and an editor, a formatter or another session may have changed files since. The rollback below relies on this check. It can only undo this command's own changes safely if it knows nothing else was changed when those changes began.

**Keep a list of every path this command touches.** From step 4 onward (or from the first write in step 2), write down each path as it is touched. For each one, record its kind, and the blob id of what this command last wrote there. A blob id is git's fingerprint of a file's content. Get it with `git hash-object -- <path>`, run right after that write. The kinds are:

- `created`: a file that did not exist before this run — `.dev-team/.gitignore`, `.dev-team/README.md`, and `.dev-team/config.yml` if it was absent. Also note whether this run created the `.dev-team/` folder itself.
- `moved`: the old legacy root name and the `.dev-team/<name>` it moved to. The blob id of a moved file is taken right after `git mv`, and taken again (replacing the first) after step 6 stamps it. *Why both:* if a later file's `git mv` fails at step 5, the files already moved must still be checkable before they are undone. A `git mv` that itself fails adds nothing to this list for that file: the old name is untouched (still at the legacy root, still holding what it always held) and the new name does not exist (git never created it), so there is nothing yet to record and nothing for the rollback below to undo.
- `edited`: a file tracked at H0 that this command changed — `.dev-team/autopilot.json`, a tracked `.dev-team/config.yml`, and each instruction file given the pointer sentence.

- *Why:* the rollback below undoes only the paths on this list. The blob ids let it notice when something other than this command changed one of those paths afterwards, in which case undoing would destroy that other work. If this command's own write to a listed path later fails partway — for example step 6's stamp, on a path that already carries a post-mv id recorded at step 5 — the command clears that path's recorded id right then, before the rollback below runs, rather than leaving the stale pre-failure id in place for point 3 to trip over.

4. **First write into `.dev-team/`** (conventions point 7): `mkdir -p .dev-team`; if `.dev-team/.gitignore` is absent, create it containing exactly one line, `loop.lock/`; if `.dev-team/README.md` is absent, create it with the fixed text from that section, copied from `conventions.md`, never retyped from memory. Never overwrite either file once it exists. Never edit the project's own `.gitignore`. If this step fails, stop and follow the rollback below.
5. `git mv <name> .dev-team/<name>` for each file. Moving with `git mv`, rather than copying, keeps the file's history attached and makes the change show as a rename. If this step fails, stop and follow the rollback below.
6. **Stamp the marker.** For a markdown file: if a marker (either form) is in the first three lines, remove that line; then make line 2 the new-form marker for its kind, exactly as listed in the conventions section (for example `<!-- dev-team: ledger=features schema=1.0 -->`), pushing the rest of the file down one line. Change nothing else in the file. For `verdict.json`: add the top-level field `"dev-team": "ledger=verdict schema=1.0"`, keep every other field and value, and confirm the result is valid JSON (`jq empty`). A verdict file written before `schemas/verdict.schema.json` existed may not match that schema; this command does not reshape it, because reshaping is the review skill's job on its next run. *Move first, stamp second, in that order:* an earlier wording of the underlying rule (`conventions.md` point 4) added the marker before moving the file, which means writing marker-bearing content to a path still at the top level — exactly what the ledger guard's Rule 1 refuses. Doing it in this order, `git mv` first, keeps the marker write inside `.dev-team/` the whole time. If this step fails, stop and follow the rollback below.
7. **Rewrite `.dev-team/autopilot.json` values** (conventions point 5, last bullet). If the file exists and its `schema` major is `1` (or the field is missing, which counts as `1.0`): in the `queue` values, each `gate_ledger[].spec_ref`, and `trajectory_ref`, change each string value that is exactly one of the seven names, or starts with one of them followed by `#`, to the `.dev-team/` form — the legacy root value `PROJECT.md#Backlog` becomes `.dev-team/PROJECT.md#Backlog`. Only the value text changes; the schema stays `1.0`.
   - Rewrite a value only when its file now lives at `.dev-team/<name>` — moved in this commit, or already there. A value that names a file left at the legacy root (group (c), (d), a conflict, or "leave it") stays as it is and is listed in the report. *Why:* pointing it at a `.dev-team/` file that does not exist would quietly lose the reference to where those records actually are; the next autopilot RECORD resolves it through the lookup order, which asks rather than guessing.
   - Edit the values in place rather than re-writing the whole file through `jq`, so the diff shows only those values. Then check: the file is still valid JSON (`jq empty`), and apart from the rewritten values nothing changed (compare `jq -S .` of the old file, with the same rewrites applied, against `jq -S .` of the new one).
   - An unrecognised newer `schema` major → do not touch the file; say why (its shape may have changed underneath this command).
   - If this step fails, stop and follow the rollback below.
8. **Check what was written.** Re-read line 2 of every moved markdown file (for `verdict.json`, the `"dev-team"` field). If the marker is missing, report the move as failed, do not commit, and follow "If any step from 4 to 9 fails, or the standalone commit in step 2 fails" below. ## What this command cannot do

- **The shape tests are a best-effort pattern match, not proof.** A project's own file can happen to look like a ledger (it will be asked about, never moved without a yes), and a real ledger can fail every test (it will be left alone; a person can add the marker and run the command again). Only the marker is proof, which is why only (a) moves without asking.
- **It cannot tell an old unmarked ledger full of records from a project document with records appended.** Both are sorted (d) and left alone. Real old ledgers with three or more records of their own kind land here, so a person has to add the marker by hand before this command will move them. That is the deliberate price of never moving someone else's document by mistake.
- **It cannot undo its own changes once something else has changed the repo while it ran.** The rollback then refuses and gives manual-recovery instructions instead, because an undo at that point could destroy the other program's work.
- It does not look for ledgers anywhere except the top level of the repo, and does not follow submodules or nested repos.
- It does not cut a mixed file apart, merge a legacy root file into an existing `.dev-team/<name>`, or delete anything.
- It does not rewrite references to the old names inside the moved files or elsewhere in the project (for example a link in a project's own `README.md`); it lists none of them either. Readers accept both forms through the lookup order.
