# Independent critique of the 2.0.0 implementation plan

Checked 13 September 2026 against the committed tree on `claude/ledger-file-clashes` (nothing changed; experiments only in a `mktemp` folder). Every file the plan says it will change exists at the path named, and the "extend X" claims hold where I could check them (`conventions.md` points 3, 4, 7 and 9; `loop-runtime.md` lock/recovery text at lines 107–108 and 166–170; `guard-ledgers.sh` Rule 1 name list at line 330; `check-update.sh` throttle pattern; `dev-team-sync-branches.md:7` shim call; `verdict.schema.json` `additionalProperties:false` at line 20 and `const` at 23; `orchestration-profiles.md:53-55` detect-first posture). The section map covers all 101 brief sections and all 55 acceptance criteria (counted, brief lines 3171–3225; the plan's numbering matches the brief's order), and F1–F31, P1–P5, R1–R4 are each placed. All 15 corrections in `orch-critique.md` §8 are applied. The problems are below.

## Problems

1. **BLOCKING — On Claude, the pause flow as written cannot run at the moment it is needed, so invariant I4 ("a paused phase never loses uncommitted work") is not met.** Claude Code's docs (costs page, fetched today) say the session/weekly limit is a seat allowance shared across all models and that sub-agent usage counts against it. So when a Claude sub-agent hits the limit, the lead's own next model call fails too: the lead cannot run `quota observe → lease pause → snapshot create` (increment 4, "Contract") because it cannot act. The `state: paused` marker in `loop.lock/holder` is therefore never written on Claude. On the next `/loop` firing after a restart, the *unchanged* reclaim rule (`loop-runtime.md:168`: "Any uncommitted working-tree changes are discarded") still runs and loses the work. The flow only works for Codex workers, where the lead survives. *Fix:* make the lossy path itself non-lossy — crash recovery **always** snapshots the dirty tree to `refs/dev-team/snapshots/<job>/<phase>/<n>` before any reset, whatever the holder file says, and the resume path restores from it; write the `paused` marker opportunistically when the lead *can* act (Codex case, or after the host's wait continues the session). Add this as increment 4's first test: "stale lock, no paused marker, dirty tree → snapshot exists after reclaim". Record in departures that on Claude the pause marker is written after the fact.

2. **BLOCKING — `git stash create` does not capture untracked files, so the snapshot loses exactly the files a mid-phase agent most often creates.** Proven in a temp repo: with `M tracked.txt`, `?? untracked.txt`, `?? sub/new.js`, `git stash create` produced a commit containing only `tracked.txt`. It also returns nothing on a clean tree, and `git stash apply` onto a still-dirty tree is meaningless (the plan never says whether the tree is cleaned after the snapshot). *Fix (increment 4, `snapshot.mjs`):* build the snapshot with a temporary index — `GIT_INDEX_FILE=<tmp> git add -A && git write-tree && git commit-tree <tree> -p HEAD -m "dev-team snapshot"` — then `git update-ref refs/dev-team/snapshots/...`; state plainly that the working tree is left untouched at pause, that `restore` runs only when the tree no longer matches the snapshot (compare `git diff --stat` against the snapshot tree), and that restore uses `git checkout <snapshot-sha> -- .` plus untracked files from the tree listing, refusing if HEAD moved. Test with an untracked file and a new directory.

3. **BLOCKING — The plan defers locking itself to increment 3, but brief 97.11 requires the lock before 97.12 (implement).** Nothing in the plan can be built "against a locked plan" if the lock is computed after three increments of building. *Fix:* lock now by hand: canonical-JSON the `contract` block in §10 with a ten-line Node script kept in `.claude/plans/orchestrator-v2/` (no engine needed), record `planHash`, `approvedAt`, `approvedBy: owner`, commit `plan-contract.v1.json` there; increment 3's `plan verify` later confirms that hash. Also fix the contract so a schema can validate it: `dependsOn: ["INC-0..INC-11"]` is not a list of ids, and `"HT-4"` is not an implementation task — list INC-0…INC-11 explicitly and move HT-4 to a `preconditions` field.

4. **IMPORTANT — Increment 0 is not "small and visible"; it is the largest increment by file count.** It creates 13 `engine/lib` modules, 15 adapter files, 11 schemas, 9 fixtures, 13 test files, the simulator harness, the event log, the TOML reader, a CI job, a new command, five docs, and edits eight existing files including the ten-site `gpt-5.5` rewording. That is what the critique (§5) asked to avoid. *Fix:* split into 0a (shim, `cli/paths/store/schema/redact/doctor`, `/dev-team-doctor`, the CI `engine` job, the fixture↔schema rule with one schema, HT-1..3) and 0b (discovery, adapters, `canonical/toml/config/log`, simulator harness, audit widening). 0a is provable in an afternoon and shows something working.

5. **IMPORTANT — The widened model-id audit will fail CI on the committed plan folder.** `.claude/plans/orchestrator-v2/deep-analysis.md` and `analysis-check.md` (committed) contain `gpt-5.5`, `gpt-6-astra`, `gpt-5.6-sol`; this plan itself names `gpt-6-astra`. The plan's allowed-location list (`model-routing.md`, `engine/data/compat/`, `tests/fixtures/`, `engine/test/fixtures/`, `CHANGELOG.md`) omits `.claude/plans/`. `audit-model-ids.sh:12-14` greps the whole tree. Also the plan says "ten sites" but lists twelve (`README.md:5,500` are extra), and `CHANGELOG.md:350` is a thirteenth. *Fix:* add `.claude/plans/` and `orchestrator_prompt.md` to the allow-list; say "thirteen sites, two of which stay (CHANGELOG)".

6. **IMPORTANT — The `mwbm-standard` preset cannot set `config.yml` keys, but the plan says it does.** F27 ("preset sets `git.default-branch: alpha`") and F13 (`git.push-after-task`) are `config.yml` keys read by hooks and skills with `grep` (`config-and-toggles.md:168-177`). A profile inside `engine/data/profiles/*.json` is invisible to those readers. `sequential: true` and per-task-type tier overrides are not in the section-86 block either. *Fix:* draw the line explicitly: `orchestrator.json` (engine keys only, schema'd) versus `config.yml` (1.x keys); the preset may only carry engine keys; `/dev-team-config init --profile mwbm-standard` *offers* the two `config.yml` lines (`git.default-branch: alpha`, `git.push-after-task: on`) the way the pointer sentence is offered; list every preset key in the schema.

7. **IMPORTANT — Non-Claude models can never reach a usable tier on a real machine, so increment 5's cross-provider review can never fire.** `classify()` turns an unknown slug into `PROVISIONAL` with confidence ≤ 0.5; there is no remote catalogue (DEP-2) and no benchmark. Codex's `codex debug models` carries no capability data (only `context_window`, `supported_reasoning_levels`, `visibility`, `priority`, `upgrade`). So the Codex configured model stays below the review floor (tier ≥ 3) unless something says otherwise, and the plan never says what. Increment 1's hard filter is also self-contradictory: "until then all TRUSTED/UNKNOWN=PROVISIONAL". *Fix:* add `engine/data/compat/openai-families.json` (family prefix → provisional tier hint, `HEURISTIC` provenance — compatibility metadata, allowed by brief 3) alongside `claude-aliases.json`, and have the `mwbm-standard` preset carry a `USER_OVERRIDE` tier for "the Codex runtime's configured model". State which canary stage applies before increment 8 (say: `PROVISIONAL`, permitted risk LOW/NORMAL, and reviews at HIGH/CRITICAL need an override until learning promotes it).

8. **IMPORTANT — Increment 1 is not buildable without the numbers.** `floors.json` rows ("encode the brief"), `weights.json` per task type, effort defaults for the brief's ranges (LOW–MEDIUM, HIGH–VERY_HIGH), the score term scales, and the cost proxy when pricing is `UNKNOWN` (every subscription model) are all left to the builder. The "cheap qualified wins" test cannot be written without a cost input. *Fix:* put the full floors table (task type × risk → preferred/minimum), the initial weights, and the effort point per range into the plan; use the existing `run-report.md` per-tier weights as the relative-cost class when pricing is UNKNOWN (extending an existing abstraction rather than inventing one), and say so in `routing.mjs`'s header.

9. **IMPORTANT — Increment 0's discovery field mapping is missing.** "Every section-7 field present, UNKNOWN where not known" leaves Sonnet to decide which Codex field becomes `lifecycleStatus` (`visibility: hide`? `upgrade` non-null?), `reasoningControls`, `latencyClass`, `runtimeCapabilities`, and what Claude discovery can fill at all (only aliases and `claude --version`). *Fix:* a two-column mapping table per verified adapter in increment 0, with the lifecycle inference rules written down ("`hide` = not listed, not RETIRED; `upgrade` set = LEGACY").

10. **IMPORTANT — The §5.1 test table claims coverage the increments do not specify.** Section 93 items with no named assertion anywhere: discovery "disappearing model", "discovery failure", "cache invalidation" (rows point at increments 0/1, whose assertion lists have none of them); convergence "loops bounded / escalation occurs / stop criteria" (`convergence.test.mjs` listed under 4 and 8, but increment 4's contract never mentions attempt caps); brownout scenarios `outage.json` and `rate-limit.json` appear in §5.1 but not in increment 8's file list. *Fix:* add the missing assertions to the increment that owns them, so the table and the increments say the same thing.

11. **IMPORTANT — The owner's schema rule is only half met: fixtures are validated, real data files are not.** The fixture↔schema pairing check proves samples validate; nothing validates `engine/data/*.json`, `engine/data/profiles/*.json`, `policy-packs/*.json`, `engine/sim/scenarios/*.json`, or the committed `plan-contract.v1.json` against their schemas in CI. Several data files have no schema named at all (`job-templates.json`, `parallelism.json`, `cost-bands.json`). `.claude-plugin/plugin.json`, `marketplace.json`, `hooks/hooks.json` are JSON files with no schema (feature-map P4 already flagged this) and the plan is silent. *Fix:* a `schemas/manifest.json` (itself schema'd) mapping every real JSON file to its schema, walked by `engine.sh schema validate --all` and by `check-jsonschema` in CI; either write small schemas for the three Claude Code manifests or record an explicit, reasoned exception in `departures.md`.

12. **IMPORTANT — `CLAUDE_PLUGIN_DATA` availability inside a skill's Bash call is assumed, not verified.** The plugins reference (fetched today) says placeholders resolve "anywhere the placeholder appears" in skill content, but does not say the variable is in the Bash tool's environment. `paths.mjs` refuses when it is unset, so every engine call from a skill would fail with exit 2. *Fix:* add HT-0 to increment 0 (run `engine.sh doctor` from a skill and from a hook, record both); give the shim a documented fallback of `~/.claude/plugins/data/dev-team-dev-team` (the documented default location) with a warning line, and allow `--data-dir`.

13. **IMPORTANT — `tests/smoke-structure.sh` "check 8 glob widened to `schemas/**/*.schema.json`" needs `globstar`, which macOS `/bin/bash` 3.2 does not have** (proven: `shopt -s globstar` → "invalid shell option name"). The file was just fixed for a bash-3.2 fault; this would re-introduce one. *Fix:* use `find schemas -name '*.schema.json'`.

14. **IMPORTANT — `projectKey` from the real path of the checkout breaks with worktrees (increment 10) and second clones.** A worktree's real path differs, so its engine process gets a different `projects/<key>/` folder: leases, competency and session ids split. *Fix:* key on the resolved `git rev-parse --git-common-dir` path (shared by all worktrees of one repository), with the root-commit hash as a second component.

15. **IMPORTANT — Rule 1's new name list does not match the files the plan writes.** The plan adds `review-contract*.json` to `guard-ledgers.sh`, but review contracts are written as `.dev-team/jobs/<jobId>/reviews/<reviewId>.json` — a name the pattern never matches. *Fix:* name the file `review-contract.<reviewId>.json`, or drop the entry. Also state that the engine writes `"dev-team"` as the first key so the marker lands on line 2 (Rule 1 only looks at the first three lines, `guard-ledgers.sh:325`).

16. **IMPORTANT — "Effort selected independently of tier" (AC 25) is not true on Claude as designed.** Effort is frontmatter-only, and the plan fixes one effort per role file (reviewer = high, architect = xhigh …). Brief 45 wants independent review at HIGH–VERY_HIGH and architecture at HIGH–VERY_HIGH; with one file per role, VERY_HIGH for a review is impossible. Increment 2's "effort variants only where the mapping needs them" leaves the file set undecided. *Fix:* enumerate the role × effort agent files in increment 2 (for example `reviewer.md` high, `reviewer-xhigh.md`, `architect.md` xhigh, `architect-max.md`, `engineer.md` medium, `engineer-high.md`, `scout.md`/`scribe.md` low), make `smoke-structure.sh`/`audit-model-ids.sh` lists match, and record in departures that on Claude the set of effort levels per role is fixed by these files.

17. **IMPORTANT — The test private key will be shipped.** "Private key only under `engine/test/fixtures/`, never shipped" is false: the marketplace installs the whole repository, `engine/test/` included, and a committed private key is exactly what the ship skill's gitleaks check flags. *Fix:* generate the test keypair at test time with `crypto.generateKeyPairSync('ed25519')` and sign the valid/tampered/expired fixtures on the fly; commit only the pinned public key.

18. **MINOR — Two spellings of the Codex effort flag.** §2.4 says `-c model_reasoning_effort="<level>"`, §8 says `-c model_reasoning_effort='"high"'`. The HANDOFF record (line ~155) shows the second form is the one that worked. Pick it and use it everywhere.

19. **MINOR — `time.mjs` is named in D1 as an isolated module but is never created** in increment 0 or 4. Add it to increment 4 (zone handling, "next occurrence" rule, tests with `Europe/London` and a date-less clock time).

20. **MINOR — Stale numbers and unnecessary keys.** `tests/scripts.bats` has 63 tests today, not 56 — say "unchanged and green", not a count. The `orchestrator:` pointer line in `config.yml` does nothing (the engine can look for the file) and adds a key the verbatim schema in `config-and-toggles.md` must then document; drop it. `quota observe --text` passes provider error text on the command line (visible in process lists); read it from stdin.

21. **MINOR — `verdict.json` ownership.** The shared-artifacts table names review as the only writer; increment 5 has the engine turning Codex output into claims. Add "engine, on behalf of the review skill" to the table row when the schema gains its optional fields.

22. **MINOR — Issue cadence.** The owner's rule (`.claude/CLAUDE.md` §6) is an issue update per task; the plan says per increment on #46. Say per package (the plan's own commit unit).

23. **MINOR — Plain English.** The plan mostly explains its terms, but "total-ordered", "fail-open", "canonical JSON", "hard filter", "compare-and-swap" appear without a one-line gloss. Add a short glossary at the top of §2, since the plan becomes a locked, owner-approved document.

## What is good and must be kept

- The decide-and-record engine / executing lead split, with I9 ("the engine never spawns a worker") as an invariant.
- Storage: nothing machine-local in the repo; per-job decision files; `orchestrator.json` with a schema; `verdict` and `autopilot` staying 1.0 with additive fields; markers and the JSON twin of the ownership rule in `store.mjs` (`readMarked`/`writeMarked`), all consistent with `conventions.md` points 3–7.
- The shim's exit-3 rule and the fixed exit-code table; "1.x behaviour continues" as a tested path, not a promise.
- Quota observations with the four causes, family-vs-session scope, recorded assumptions and confidence; `resetAt: null` → BLOCKED; re-checking the provider rather than trusting the computed time.
- The paused ≠ crashed rule (the idea is right; only its trigger is wrong — see 1).
- Remote catalogue: Ed25519 over canonical JSON, pinned key, hand-verifiable, payload schema with no fields for floors or gates, verified payload and result stored together.
- The section-98 gate as a runnable script with the Codex run id required before exit 0.
- DEP-1…DEP-12 written plainly, with D1–D4 deltas that do not require re-planning.
- The role-name rename as its own increment; increment 5 depending on 4's quota adapter; Fable re-planning each later increment at contract level.
- Widening the audit to all provider id patterns; rewording the twelve prose sites to "the Codex runtime's configured model".

## Missing

- A statement of where the plugin repository's own `.dev-team/` folder comes from when it dogfoods (`plans/orchestrator-v2.v1.json` implies creating `.dev-team/`, `.dev-team/README.md` and `.dev-team/.gitignore` in this repo) — or keep the locked contract in `.claude/plans/` as in problem 3.
- A per-job "which worker/provider is exhausted right now" view in `/dev-team-status` before increment 7 (increment 4 records observations but nothing prints them until 7's `quota status`; move `quota status` to 4's command list, where the table already has it).
- The `engine` CI job needs `pipx install check-jsonschema` too if it validates fixtures (today only the `test` job installs it, `plugin-audit.yml:33-34`).
- A hand test that a `Task` spawned with a `model` parameter also honours the agent file's `effort` (HT-2 covers model only).
- The rule that `orchestrator.json` (committed) may never carry a remote-catalogue URL with credentials or any token — the plan's safety section covers reads, not this committed-config case (brief 89 "generated committed configuration").
