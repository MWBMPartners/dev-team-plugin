### 1. (high) Subfolder fix now refuses the plugin's own writes when .dev-team/ sits at the session folder, and ignores guard: off there — refuter: confirmed

- **Where:** `hooks/guard-ledgers.sh` line 394
- **What is wrong:** After the finding-5 fix, 'inside .dev-team/' means only `<git top>/.dev-team/`, and config.yml is read only from the git top (line 242-246). Nothing in the plugin tells its writers that `.dev-team/` must be at the git top: conventions.md:56 says 'at the top of the project', and every skill writes `.dev-team/<name>` relative to the session folder (Claude Code resolves that against cwd). The Bash guard (hooks/guard-dev-team.sh:17) still reads `.dev-team/config.yml` relative to cwd, so the two hooks now read the toggle from different places in a subfolder session.
- **How it goes wrong:** Monorepo: a session started in `<repo>/packages/app` (git top is `<repo>`). The plugin writes `<repo>/packages/app/.dev-team/PROJECT.md` with the marker on line 2. Rule 1 refuses it with exit 2: 'the path ... resolves outside .dev-team/. Write it under .dev-team/ instead' — which is exactly where it already is. Setting `guard: off` in `<repo>/packages/app/.dev-team/config.yml` (what /dev-team-config init creates there) changes nothing, because the hook only reads `<repo>/.dev-team/config.yml`. Before the fix (root = cwd) the same write was allowed, so every ledger write for a sub-package session is a regression. Reproduced on bash 3.2 and 5.3: Write file_path `<repo>/src/.dev-team/PROJECT.md` with cwd `<repo>/src` -> rc 2; relative `.dev-team/PROJECT.md` from src -> rc 2; with `<repo>/src/.dev-team/config.yml` containing `guard: off` -> still rc 2.
- **Proof:** Probe output (both bashes): 'DIFF rc=2 (want 0) NEW-PROBLEM? plugin abs write to <cwd>/.dev-team/PROJECT.md from src' with the refusal text quoted above; same for the relative form and with guard: off in <cwd>/.dev-team/config.yml.
- **Fix:** Treat a `.dev-team/` folder at the session folder as inside too: in the in_devteam test accept `"$sub"/.dev-team/*` as well as `.dev-team/*` when $sub is non-empty (a ledger written under the session's own .dev-team/ harms no top-level file, which is all Rule 1 protects). Read `guard:` from both `<cwd>/.dev-team/config.yml` and `<root>/.dev-team/config.yml`, `off` winning from either, so the two hooks agree. Add two bats cases next to the subfolder block: an absolute and a relative `.dev-team/PROJECT.md` write from src must exit 0, and `guard: off` in src/.dev-team/config.yml must be honoured. Alternatively, if the intended rule is that `.dev-team/` always lives at the git top, say so in conventions.md point 1 and make the writers (and /dev-team-config init) use `git rev-parse --show-toplevel` — the hook and the skills must agree on where .dev-team/ is.
- **Refuter's reason:** Reproduced on /bin/bash 3.2 and bash 5 with cwd=<repo>/src. A marker Write to the absolute <repo>/src/.dev-team/PROJECT.md is denied, and so is the relative .dev-team/PROJECT.md. It is still denied with 'guard: off' in <repo>/src/.dev-team/config.yml. The pre-fix hook allowed the relative write (rc 0), so this is a regression for sub-folder sessions. conventions.md only says 'at the top of the project', which does not settle where .dev-team/ lives in a monorepo.

### 2. (medium) Rollback point 4 aborts completely if the list carries the target of a git mv that failed — refuter: confirmed

- **Where:** `commands/dev-team-move-ledgers.md` line 149
- **What is wrong:** Point 4 undoes everything with ONE `git restore --source=<H0> --staged --worktree -- <every moved old name> <every moved .dev-team/<name>> <every edited path>`. Git refuses the whole command, restoring nothing, when any pathspec matches nothing in H0 or the index. Point 3 (line 148) says a path 'whose own write failed partway has no id yet; it is undone without this check', and line 128 says a moved file's id is taken after git mv — so the text invites listing the file whose `git mv` failed (its `.dev-team/<name>` never existed).
- **How it goes wrong:** Walk of a failure at step 5: FEATURES.md moved fine, then `git mv SECURITY.md .dev-team/SECURITY.md` fails. The list holds FEATURES.md -> .dev-team/FEATURES.md, the created .dev-team/.gitignore and README.md, and (read literally) SECURITY.md -> .dev-team/SECURITY.md with no id. Point 4's restore includes `.dev-team/SECURITY.md`; git answers 'error: pathspec '.dev-team/SECURITY.md' did not match any file(s) known to git', exit 1, and leaves the rename staged and the created files in place. Point 5 then reports leftovers and the manual-recovery text — the rollback has failed in the very case finding 2 was fixed for. Reproduced in a throwaway repo: status before and after the restore identical ('R FEATURES.md -> .dev-team/FEATURES.md', '?? .dev-team/.gitignore').
- **Proof:** git restore --source=$H0 --staged --worktree -- FEATURES.md .dev-team/FEATURES.md .dev-team/SECURITY.md -> 'error: pathspec ... did not match any file(s) known to git', rc=1, `git status --porcelain --untracked-files=all` unchanged.
- **Fix:** State in the list paragraph (line 128) that a `git mv` that fails adds nothing to the list (the old name is untouched and the new name does not exist), and in point 4 restrict the restore to paths that exist in H0 or the index (`git cat-file -e <H0>:<path>` or `git ls-files --error-unmatch -- <path>`), or run one `git restore` per path so one unmatched path cannot cancel the others. Extend the bats restore test with a never-existing `.dev-team/SECURITY.md` in the pathspec to pin the chosen behaviour.
- **Refuter's reason:** Throwaway repo: after git mv FEATURES.md into .dev-team/, running git restore --source=H0 --staged --worktree on FEATURES.md, .dev-team/FEATURES.md and a never-existing .dev-team/SECURITY.md gave 'error: pathspec ... did not match', rc=1. Status was unchanged (the rename stayed staged). Without the missing path it succeeded. The text says paths are listed 'as each is touched' and exempts partly failed writes, so a failed mv target plausibly ends up on the list.

### 3. (low) A stamp that fails partway makes the rollback refuse for the wrong reason — refuter: confirmed

- **Where:** `commands/dev-team-move-ledgers.md` line 148
- **What is wrong:** A moved file's blob id is taken right after `git mv` and replaced only after step 6 finishes stamping (line 128). If the step-6 write to `.dev-team/<name>` fails partway, the recorded id is the post-mv one and the file now holds partial content. Point 3 then sees a mismatch and treats it as 'something else changed it', so nothing is undone and the manual-recovery text is given, even though only this command touched the file. Point 3's exemption ('has no id yet') does not apply because the path does have an id.
- **How it goes wrong:** Step 6 dies halfway through rewriting `.dev-team/FEATURES.md` (disk full, tool error). Rollback point 3: hash-object of the half-written file != recorded post-mv id -> 'do not undo anything'. The person gets manual-recovery instructions for a tree that the command could safely have restored (no data loss, but the promised undo does not happen).
- **Proof:** Text reading of lines 128 and 148; no experiment needed — the rule as written cannot distinguish its own partial write from a foreign edit.
- **Fix:** Say that when a write to a listed path fails partway, the command clears that path's recorded id before entering the rollback, so point 3 skips the check for it (the rest of the list is still checked).
- **Refuter's reason:** From the text: line 128 takes a moved file's blob id right after git mv and replaces it only after step 6 stamps. The point-3 exemption covers only a path that 'has no id yet'. A half-finished stamp therefore leaves a stale id that does not match, and point 3 refuses to undo, even though only this command touched the file. The inconsistency is in the text as written.

### 4. (medium) The two 'never touches the real repo' guard tests only catch the exact two old patterns — refuter: confirmed

- **Where:** `tests/scripts.bats` line 1083
- **What is wrong:** The patterns are `rm -[rf]+ "\$REPO_ROOT` and `> "\$REPO_ROOT/`. They miss `mkdir -p "$REPO_ROOT/..."` (the exact line the old dangerous .claude/agents test used), `rm -rf "${REPO_ROOT}/..."`, unquoted `$REPO_ROOT/...`, `cp ... "$REPO_ROOT"/x`, `printf x > "$REPO_ROOT"/x` (quote before the slash), `tee`, `mv`, `touch`, and deletion through a derived variable such as `rm -rf "$MOVE_LEDGERS_MD"`.
- **How it goes wrong:** A future test adds `mkdir -p "$REPO_ROOT/.claude/agents"` and forgets to clean up. Both guard tests stay green, and from then on scripts/audit-model-ids.sh fails on that contributor's machine ('.claude/agents/ exists'). Reproduced: a scratch copy of scripts.bats with seven such lines added — only `rm -rf "$REPO_ROOT"/x` was caught; `mkdir -p "$REPO_ROOT/…"`, `rm -rf "${REPO_ROOT}/…"`, `cp x "$REPO_ROOT"/…`, `printf x > "$REPO_ROOT"/…`, `> "${REPO_ROOT}/…"` and `rm -rf "$MOVE_LEDGERS_MD"` all passed the 'no test writes a file directly into the real repository' test.
- **Proof:** bats -f 'scripts.bats: no test' on the probe copy: test 1 failed only because of the `rm -rf "$REPO_ROOT"/x` line; test 2 passed with all the write variants present; `grep -nE` with each pattern listed exactly one caught line.
- **Fix:** Broaden both patterns: for deletes/creates something like `(rm|mkdir|cp|mv|tee|touch|ln)\b[^|&;]*\$\{?REPO_ROOT` and for redirects `>>?[[:space:]]*"?\$\{?REPO_ROOT`, allow-listing the read-only branch-hygiene `cd '$REPO_ROOT'` line if it matches, and also grep for `\$MOVE_LEDGERS_MD` on any rm/redirect line. Keep the self-exclusion trick (string concatenation) so the test's own lines are not matched.
- **Refuter's reason:** The patterns at scripts.bats:1083-1093 are literally 'rm -[rf]+ "$REPO_ROOT' and '> "$REPO_ROOT/'. Neither matches mkdir -p "$REPO_ROOT/.claude/agents", which is the very kind of line that caused finding 11, nor ${REPO_ROOT}, cp, tee or a quote placed before the slash. The tests claim more than they check.

### 6. (low) A cwd with a trailing slash defeats the new prefix strip — refuter: confirmed

- **Where:** `hooks/guard-ledgers.sh` line 233
- **What is wrong:** `case "$base" in */"$prefix")` needs cwd's text to END in the prefix. A cwd of `<repo>/src/` does not, so $root stays `<repo>/src/`, the top-level file is judged absolute-and-outside, and Rule 2 skips it. Claude Code normally sends cwd without a trailing slash, so this is a corner, and the pre-fix hook allowed the same write, so it is not a regression.
- **How it goes wrong:** Payload cwd `<repo>/src/`, Edit adding `F-001` to `<repo>/SECURITY.md` with `.dev-team/loop.lock/` at the top -> rc 0 (both bashes); the same payload with cwd `<repo>/src` -> rc 2.
- **Proof:** Probe line 'DIFF rc=0 (want 2) cwd with trailing slash, abs top SECURITY.md' on bash 3.2 and 5.3.
- **Fix:** Right after `base="${cwd:-$PWD}"`, strip one trailing slash when the result is longer than '/': `[ "$base" != / ] && base="${base%/}"`. One-line bats case.
- **Refuter's reason:** Reproduced on both bashes. An Edit adding F-001 to <repo>/SECURITY.md with cwd '<repo>/src/' returned rc 0; the same payload with cwd '<repo>/src' was denied (rc 2). It is a minor corner case and not a regression, as the reviewer says.
